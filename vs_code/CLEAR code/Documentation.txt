Section one, Intro:

The CLEAR code is a multi-purpose code designed to work with most VEX V5 robots with minimal modifications. This code is large, but it is designed to run lightly when not recording. This makes it usable with very big or resource-intensive programs. Also, it is compatible with blocks because it uses Python and can be copied, pasted, and placed in a switch block to run in blocks. Our primary goal is to make it easy for any team to use and to help many teams with worn or faulty parts or robot issues. It has five main functions: Capture, Log, Encoding, Archiving, and Recording. This is why it is named CLEAR. The most fundamental components are capture and logging so we will start with them next.

Section two, Capture:

The most fundamental component is the capture code, which can capture most of the information the robot provides. Given the code's highly customizable nature, we will focus primarily on the standard features of the Logging object. The first thing is that the controller logging will log all buttons and stick axes, and it can support both controllers. It can also monitor the motors and provide warnings about power and temperature. It does not give simple data about the motors. The last logging object is the drivetrain. The drivetrain is a separate object that can monitor a two-, four-, or six-motor drivetrain. It captures the same data as the motors but in a more unified format and uses different logging codes. Now, this is only the standard logging, and in the code, you can configure to add loops or do one-time captures to make it capture everything you want with even the most basic of coding skills.

Section three, Logging:

Logging is part of the capture and is implemented using the main object named Log. The log.add() function takes any code in the dictionary "codes" and produces a full string to log into an SD card. The logging always tries to print to the VEX terminal, but will only log to an SD card if the card is present when the code starts. Then, the "codes" dictionary can add any code the user wants into the dictionary by a simple calling of a function every startup called log.add_codes(), this makes it a lot easier to adapt to robots with special features, This i why it is so easy to get the capture and logging to get anything that the person configuring the code wants. There is also a remove codes feature if you want to remove the codes you added. Also, you can change the codes so you can edit what you want it to say or reuse the same key for a different purpose. 

Section four, Archive:

Archiving the logging code is a big part of the code; otherwise, it will bog down the SD card and consume a lot of space after long use or recording sessions. How it works is by turning the full strings back into the codes that made them. This makes a much smaller file that will not bog down the SD card nearly as fast. Then, because of the extra space used, it can load the full log into memory and fetch additional lines from the log history. Also, you can recall archived data to improve readability and identify issues that occurred across multiple runs.

Section six, Encoding:

Encoding in this code means converting log strings into Python function calls that the robot can execute quickly. The encode function processes logged data, maps the correct button inputs to functions preconfigured by the coder, and translates them into runnable Python code. Each function call can have up to 21 variables, representing different actions or settings. These functions and their activation buttons should operate similarly to the driver control functions (used during manual operation), so that automatic playback is as accurate as possible.

Section seven, Other:

Throughout the code (see section zero), you will see many "try:" and "except MemoryError:" statements. These are error-handling techniques in Python—when a MemoryError occurs, it means the computer does not have enough memory to complete a task, often because SD card files are large. In these cases, the program reads files line by line to avoid memory overflow, which is slower but safer. In the Log object’s __init__ function, there is also an "except OSError:" block. OSError in this context refers to an operating system error, often triggered when memory is full, that can prevent loading necessary Python libraries. By handling these errors, the program avoids crashing and prevents memory overflow at startup, even under resource constraints.

Section eight, Functions and their uses:

Now I will go into detail on how the capture works and its current capabilities.

there are four main functions used in the default use of the Capture the log.capture.battery(), log.capture.controller(), log.capture.motor(), log.capture.drivetrain, and log.capture.variable().

First, the battery function. There are no inputs for this function, as there will always be one battery and the information will always be the same. It captures capacity, voltage, and current. If the battery capacity is 50% or lower, it will give a warning; if it is below 25%, it will log an error. For the voltage, if it is below 12 volts, a warning will be displayed; if it is below 11 volts, an error will be logged. About the same as the voltage, but if the amps are higher than 15, I'll warn, and 18 will trigger the error log.

Next is the controller function, which can accept either controller with a simple input of 1 or 2, and you can use the monitor motors to capture how far the motors moved relative to the sticks. The function will capture all button states and the stick position for both controllers and log them, even if all buttons are pressed. To prevent spam, it will log only when it is pressed and released, and the sticks only if they differ from the last time they were checked.

Then there are the motors, which are like the battery: they only log when there is something of note, so they log power and temperature. The only input is the motor you want to log.
For the temps, if they are 50% or more, it will log a warning; if over 70%, it will log an error. same for power, but 11 and 20 respectively. Once the motor's check value returns to normal, it will log the event to make the log more readable and provide more useful data.

Next, the drivetrain. This is similar to the motors, but you need to add another '.' to specify whether it is a two-, four-, or six-motor drivetrain, and enter the motor names in the correct place in the input order. The logging is very similar to the motor function, and all thresholds are the same. However, the code used is different, and it will show which one is the problem in the drivetrain. Then the readout is slightly different: it will not only show the peak usage of the data but also the total, making it much more useful for drivetrain-related issues.

last is the variables this one is pretty simple and with log the initial value and any changes to the value and logs it the input needed are its name in quotation marks and the value by calling that variable.

Section ten, Performance:

During the state competition, when we were talking about the logging, one of the judges asked about its performance. We couldn't fully answer this question, but it's fairly light. We can now say with full confidence that the software is lightweight and will have minimal impact on the robot's performance during logging.

We measure performance by how long it takes to complete, since we can't observe CPU utilization in the brain. Next, the setup we used logs six motor drivetrain motors, three other motors, two variables, 5 sensors, and one controller to test the performance of a pretty big robot we would make; We also used the brain read to make it slower to. For the full loop, which logs everything 200 times over the time when logging is about 40600 msec, it varies by about +- 200 msec total. Now, every loop in the outer loop has a 200msec minus the time for the loop wait to make it work at 5 Hz. Hence, we spend about 600msec busy, which is ~1.52% of the time, and it also uses the Thread function because of that it runs in the background without affecting the main program's performance. It runs its tasks when the brain is idle, and, on top of that, we can't even notice any lag in input. So this led us to believe that it is indistinguishable from a brain without it.
