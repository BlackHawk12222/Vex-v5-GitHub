this is the documentation of the CLEAR code:

Section one, Intro:

The CLEAR code is a multi purpose code that is designed to work with most vex v5 robots with minimal code changes
it has five main functions Capture, Log, Encoding, Archiving, Recording. This is why it is named CLEAR the most fundamental parts is the capture and log so we will start with them next.

Section two, Capture:

The most fundamental part is the capture the code is capable of capturing a lot of the info the robot gives. because of the very customizable nature of the code, we will talk mostly about the standard things in the Logging object. The first thing is the controller logging it will log all buttons and stick axis and can do both controllers. It can also monitor the motors as it will give warnings about things like power and temps it does not give simple data about the motors. The last of the logging object is the drivetrain, the drivetrain is a separate object and can monitor a two motor, four motor, or a six motor drivetrain and monitors the same as the motors but as a more unified capture and uses different codes for the logging.

Section three, Logging:

The logging of the code is part of the capture and is the main object named Log. The log.add() function takes any code in the dictionary "codes" and produces a full string to log into an sdcard the logging always try's the print into the vex terminal but will only log into an sdcard if the card is in when the code starts. Then, the "codes" dictionary can add any code the user wants into the dictionary by a simple calling of a function every startup called log.add_codes(), this makes it a lot easyer to adapt to robots with special features.

Section four, Archive:

Archiving the logging code is a big part of the code as if it is not it will bog down the sdcard and take up a lot of space after long use or long recording sessions. How it works is by turning the full strings back into the codes that made them. This makes a much smaller file that will not bog down the sdcard nearly as fast.

Section five, Recording:

recoding with this code is very different than the code that was originally intended. It works by using the capture of the code, because of the code using a time based movement we need the polling of the capture to be VERY fast in the current config we have it does from 5 Hz to 1000 Hz to do this it uses a Cashe and after looping the capture 300 times will unload the Cashe and put it into the Aton file and the log file. Even with this casheing it is very resource intensive and will take a while to encode and a lot of battery.

Section six, Encoding:

The encoding is simple in idea but a pain to make it work as it takes the logs strings and makes them into the function calls that the encode function inputs provide with the button than activates them and turns it into the exact python code needed to run it as fast as possible.
